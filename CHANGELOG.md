# Changelog

# v2.2.0 (2026-11-06)
- **New: send a webhook again from an entry's page.** Gravity Forms sends a webhook once, when the entry comes in (with retries in the background, as the attempts settings allow), and offers no way to send it again: if CiviCRM was down, or the webhook was turned off at the time, that entry never reached CiviCRM. A "Webhooks" box on each entry's page now lists the form's active webhooks, with how each last went for that entry ("not sent yet", "sent 6 Nov 2026 14:02", "failed ..."), and sends the chosen one straight away. The box shows the result in plain words: sent; the server answered with an HTTP error; the answer wasn't JSON; or CiviCRM's own error message. The webhook is sent the way Gravity Forms' background processor sends it, so this plugin's CiviCRM formatting, timeout and failure email apply, the entry's feed status is updated, and "Delete entries after Webhooks are completed successfully" deletes the entry when it succeeds (the box says so). It sends even if the webhook was already sent or its condition doesn't match the entry (marked "[condition not met]"), since the admin chose it, and adds an entry note saying who sent it and how it went. Only for users who can edit entries; webhooks that are turned off, or belong to another form, are refused
- **New: activating this version deactivates an older copy of the plugin in another folder.** Moving a site from 2.0.0 or earlier is a manual upload, and WordPress installs the new version beside the old copy (their folders differ) rather than over it. Activating the new copy now deactivates the old one, in the same scope (the site, or network-wide), and a notice names its folder and version with WordPress's own link to delete it. The notice goes once the old copy is deleted. Nothing is deleted without the admin. So the upgrade from 2.0.0 is: upload the zip, click Activate Plugin, then Delete the old copy from the notice
- **Release workflow: a version's zip can never be replaced.** 2.1.0's workflow refused to replace a published release's zip, but a tag pushed again (whose release GitHub turns back into a draft) could still swap it, and a failed lookup of the existing release was read as "no zip there yet". The workflow now looks the release up including drafts, stops on any API error, refuses a different zip whether the release is published or a draft, re-publishes when the zip is the same one (a re-run), and never overwrites an asset (`--clobber` is gone). To replace a zip that no site can have installed, delete the release first
- **Fixed: creating or updating a webhook outside Gravity Forms' admin screens was a fatal error** (`Call to undefined function gform_tooltip()`). `GFAPI::add_feed()` and `update_feed()` build the webhook's settings to know which to encrypt, from WP-CLI, the REST API or an import, and this plugin's settings called a function Gravity Forms only loads on its admin screens. It now loads it first, as Gravity Forms does
- The README's "Other settings" and the rest are now one "Other features" section: the form settings, each webhook's own settings (failure notification email, request timeout, attempts), and sending a webhook again
- `tests/run.sh` covers both new features. The upgrade from the real 2.0.0 zip now checks that activating the new copy deactivates the old one, that the notice names it with a working delete link, and that deleting it from there leaves the new copy active and the notice gone. Sending a webhook again is tested against the real Gravity Forms and Webhooks add-on, with a stand-in for CiviCRM, when `GFCFP_TEST_GF_DIR` names a folder with their zips (Gravity Forms isn't free, so CI skips it): success, an HTTP 500, a CiviCRM API error, an answer that isn't JSON, a webhook that is off, another form's webhook, a bad nonce, a user who can't edit entries, and the delete-entries setting

# v2.1.0 (2026-11-06)
- **New: updates from GitHub.** WordPress now offers each new GitHub release of this plugin on the Plugins page like any other plugin's update: the update notice, "Update now", and the plugin's "Enable auto-updates" link. [`blackbricksoftware/wp-artifact-updater`](https://github.com/blackbricksoftware/wp-artifact-updater) 1.5.0 (its `GitHubReleases` source, public) finds the newest release and downloads its zip; it ships in the zip's `vendor/`. The repository is public, so no token is needed. The new `Update URI` header routes WordPress's update check for this plugin to it, and stops wordpress.org from ever offering a different plugin with the same folder name
- **Updates install into the folder the plugin is already in** (the library's `InstallFolder`). Release zips up to 2.0.0 had no folder inside them, so sites that installed one have the plugin in a folder named after the zip, `gravity_forms_civicrm_form_processor/` (on WordPress 7.1.4 and later, that name plus random characters), while 1.0.0's zip, a git clone and composer use `gravityforms-civicrm-form-processor/`. WordPress installs an update into the folder its zip names, and when that differs from the plugin's folder the plugin ends up deactivated. The unpacked update is now renamed to the plugin's own folder first; one whose zip has no folder inside is refused
- Updates are offered, never forced: nothing turns on auto-updates. Dashboard › Updates › "Check again" asks GitHub straight away (the library's `CheckAgain`), rather than answering from the 6-hour cache. Sites where a deploy owns the plugins switch updates off with WordPress's own `DISALLOW_FILE_MODS`. Both library extras are registered by the plugin itself, so they work even when another plugin on the site ships an older copy of the library
- **Fixed: with Gravity Forms inactive, every request on the site was a fatal error** (`Class "GFCommon" not found`, on `init`). The plugin file now hooks everything in one `plugins_loaded` callback, laid out like our other plugins: if its classes can't be loaded (a GitHub "Source code" zip has no `vendor/`) it does nothing, and without Gravity Forms it registers only the updater, so an update can still be installed. The file's one constant is `GRAVITYFORMS_CIVICRM_FORM_PROCESSOR`, its own path
- **Upgrading from 2.0.0 or earlier is a manual install, once,** since those versions have no updater: upload this release's zip on Plugins › Add New › Upload Plugin. If the plugin is in a folder named differently (`gravity_forms_civicrm_form_processor/`, say), WordPress installs the new version beside it in `gravityforms-civicrm-form-processor/` rather than replacing it, and the Plugins page lists the plugin twice; activate the new copy, then deactivate and delete the v2.0.0 one. Tested through the real upload screen, from the 2.0.0 release zip, with both copies active in between Nothing is lost: the plugin's form and webhook settings are stored by Gravity Forms
- The version header has no `v` any more (`2.1.0`, not `v2.0.0`). WordPress compares it as written, and PHP sorts `v2.1.0` below `2.1.0`, so a site would have been offered the version it already runs, forever. Tags keep their `v`
- **Requires PHP 8.2**, as 2.0.0 already did in practice (its dependencies need it); the new `Requires PHP` header stops WordPress installing it from an upload, or activating it, on an older PHP. Composer's runtime platform check is off (`platform-check: false`): on an older PHP it would answer every request on the site with a 500. Composer resolves dependencies for PHP 8.2.35 (`config.platform`), so a `composer update` on a newer PHP can't pick versions 8.2 can't run
- **Packaging:** the release zip is `gravityforms-civicrm-form-processor-vX.Y.Z.zip` with one `gravityforms-civicrm-form-processor/` folder inside, built by `bin/build.sh`: it installs the composer dependencies from `composer.lock` into a staged copy (`--no-dev --optimize-autoloader`), checks that the header, this changelog and the tag name the same version, and lints every shipped file on PHP 8.2. `composer.json`, `composer.lock` and the README's images no longer ship. Deleting the plugin removes the updater's cached release lookup (`uninstall.php`)
- **Release workflow:** pushes to master, pull requests and `v*.*.*` tags build the zip and test it in a throwaway WordPress (`tests/run.sh`), and a tag publishes that same zip to the tag's GitHub release, with this changelog's entry as the notes. The zip's SHA-256 is taken when it is built and checked before publishing, a published release's zip is never replaced, and a failed tag lookup stops the job rather than marking the release Latest. Actions are pinned to commits and composer and WP-CLI to exact versions, since sites install what the workflow publishes
